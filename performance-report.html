Streaming performance

Results for the streaming path, from the original design to the current build. Every build ran the same workload: a 14-second model answer on a 1-core service instance.

Environment
Service instances with 1 CPU and 1 GB each · PostgreSQL with 2 CPUs
Model
Fake model calibrated to gpt-5.6-luna for length, chunk sizes and timing; real-model runs where stated
Builds
Before · v1 · v2 · v3, then the stability and gap fixes
Updated
2026-10-21

Summary

  • One 1-core instance carries 64 live long answers within about 2 s of model time, up from 16.
  • At the same load, an answer costs 73% less service CPU and 87% less database CPU. The limit is now the instance's CPU, so capacity grows by adding instances.
  • On the current build, no accepted answer failed in any overload, three-instance or database-restart run.

Capacity

One instance, one reader per answer, load rising from 16 to 128 answers streaming at once. Hover a chart, or focus it and use the arrow keys, to read every build at one load.

Current build

After the stability and gap fixes, one instance at 64 at once completes 4.3 answers per second, an answer takes 14.8 s, and the first text appears in 2.1 s. At 128 at once it completes 6.9 per second with 0 failed answers.

Memory

Peak memory of one instance against answers streaming at once. Memory is not the limit.

  • A live long answer costs about 1.1 MB in v3, down from 2.1 MB in v2, where every small chunk was its own object.
  • An idle instance uses about 195 MB. By memory alone, about 760 live answers would fit in 1 GB; CPU stops the instance near 64.
  • Held output is capped at 4 MiB per answer and 256 MiB per instance, so even the worst case stays inside the container.

Cost per answer

One long answer, before and after, on the same workload. Each row is scaled to its own before value.

Commits per answer fell from 456 to one per model step; a plain answer is a single commit. In larger runs the kept rows settle at about 19 KB per answer. Most of that is bookkeeping, such as the saved model input that lets an approval or Retry continue exactly.

Before raising the cap

  1. Re-measure the per-instance cap on the production hardware. These figures come from 1-core local containers; keep maxActiveTurns at 64 until the same load passes there.
  2. Plan database connections. Each instance opens 19: 16 runtime, 2 maintenance, and 1 listener that needs a direct connection, not a pooled one.
  3. Confirm long streams pass the gateway. An answer is one long-lived POST response; proxies must not buffer it or time it out early.

Method. Local containers, each service instance limited to 1 CPU and 1 GB, PostgreSQL on 2 CPUs. "At once" counts answers streaming at the same time; "answers per second" counts completed answers. The fake model replays answers calibrated to gpt-5.6-luna; rows marked "real model" used the real provider.

Not covered: production hardware, network latency to the model provider, and gateway behavior.
